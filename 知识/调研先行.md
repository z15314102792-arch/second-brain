# 调研先行原则

## 核心结论

**最重要要求：不要重复造轮子。** 很多灵感、项目、解决办法、代码结构、UI 交互、部署方式、排错思路，GitHub、技术社区、同类产品和第二大脑历史记录里已经有成功案例。AI 助手的默认动作不是重新创造，而是先找成熟案例，直接照搬可复用部分，或在用户场景下做必要改造。

**Why:** 用户在多次合作中发现，直接上手写代码会导致基础问题一犯再犯（如 CSS z-index 层级覆盖 Canvas、横屏检测用 `innerWidth > innerHeight` 而非 `matchMedia` 等）。这些问题在同类产品中早已有成熟的解决方案，不需要重新踩坑。

**How to apply:**
1. 接到需求后，先搜索同类产品的实现方案、开源项目、社区教程、成功案例、第二大脑历史记录
2. 了解常见的坑和最佳实践（如移动端横屏用 `screen.orientation` + `matchMedia` 而非 `innerWidth`）
3. 优先复用或借鉴成熟方案：代码结构、提示词、工作流、UI 交互、部署方案、排错步骤都可以借鉴
4. 调研完再出方案，方案里写明参考了哪些资料、借鉴了什么、为什么适合当前任务
5. 方案确认后再写代码
6. 禁止跳过调研直接编码，除非任务非常小且明显不需要外部方案
7. 同一问题卡住时，停止反复微调，先查别人怎么解决，再回来验证

## 额度控制

调研先行不是无限调研。已明确工具、明确版本、明确执行路径时，只做来源校验和必要验证，不重新扩大搜索。

轻量调研、README 摘要、社区方案初筛，优先交给 Gemini/低成本模型；但如果调用其他模型需要传大量上下文、复核成本接近当前 Codex 直接完成，就不要为了形式分级而增加总消耗。详见 [[知识/低消耗分级执行]]。

## 判断标准

- 有成熟开源项目能用：直接参考它的架构、功能拆分、交互和实现方式
- 有社区踩坑记录：先按社区验证过的方法处理
- 第二大脑已有相关项目：先读旧项目和日志，不重复总结
- 国内不可用、收费过高、小白难操作的方案：只借鉴思路，不直接照搬
- 找不到合适案例：再从零设计，并记录为什么不能复用现成方案
