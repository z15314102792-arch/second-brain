### ★★★ [Breaking Claude Code Opus 5 Auto Mode](https://embracethered.com/blog/posts/2026/breaking-claude-code-opus-5-and-automode/)
- **发生了什么**：安全研究人员成功突破了 Claude Code Opus 5 的 Auto Mode 安全限制。文章详细展示了攻击手法，包括如何通过精心构造的提示词或恶意输入，让 AI 编码助手在自动化模式下执行非预期操作。这延续了该团队之前对 Claude Code 系列模型的一贯安全测试思路，说明即使是新一代旗舰模型，其自动化安全边界仍然存在可被利用的缝隙。
- **为什么重要**：AI 编码助手（如 Claude Code、GitHub Copilot）正在成为开发者日常工具链的一部分，但它们往往被授予了访问代码库、执行命令的权限。一旦 Auto Mode 被绕过，恶意代码或提示注入可能导致数据泄露、代码被篡改甚至供应链攻击。这对整个 AI 辅助开发工具的安全性提出了严峻警示——自动化程度越高，安全责任越大。
- **跟我有啥关系**：如果你在开发流程中使用了 AI 编码助手，这条新闻提醒你要注意权限边界——不要让 AI 助手在无人监督的情况下执行高危操作（如 `rm -rf`、推送代码、修改生产配置等）。同时，在引入第三方 AI 工具生成的代码时，保持人工审查的习惯。
- **分析**：亮点在于安全研究人员的持续投入让模型厂商无法松懈；潜在风险是这类漏洞披露后，可能被黑产利用；值得跟进的是 Anthropic 官方对该漏洞的修复速度与修复策略，以及后续是否有针对性的加固措施。

### ★★★ [How to build a diffusion language model](https://kuleshov-group.github.io/blog/blog/2026/how-to-build-a-diffusion-language-model/)
- **发生了什么**：康奈尔大学 Kuleshov 团队发布了一篇硬核技术博客，手把手教读者如何从零构建一个扩散语言模型（Diffusion Language Model）。内容涵盖扩散模型的数学基础、文本域的训练技巧、采样策略等，并附有代码示例。同期发布的还有关于 Continuous Diffusion Language Models (CDLM) 的深度文章，显示该方向正在快速升温。
- **为什么重要**：当前主流大模型（GPT、Claude、Llama）都是自回归架构——逐 token 生成。扩散语言模型则采用“先噪声后去噪”的并行生成范式，理论上生成速度更快、控制力更强。这是大模型架构层面的前沿探索，可能影响下一代模型的设计方向。
- **跟我有啥关系**：虽然我们不太可能立刻用扩散模型做小游戏，但理解这股技术趋势有助于把握 AI 能力边界的变化。比如，如果未来文本生成从“逐字打字”变成“整段浮现”，AI 驱动的 NPC 对话、剧情生成等游戏场景的体验将完全不同。
- **分析**：亮点是这篇教程把门槛降到了可实操的层面，适合想深入研究的人；风险是扩散语言模型目前在文本质量上还难以匹敌自回归模型，短期不会取代；值得跟进的指标是：扩散模型在推理速度上的优势何时能转化为实际产品优势。

### ★★ [Agent memory as a file format](https://calpaterson.com/memoryfields.html)
- **发生了什么**：这篇文章提出一个大胆想法：把 AI Agent 的“记忆”设计成一种文件格式（类似 JPEG、PDF 那样的标准格式）。作者认为，当前 Agent 的记忆都困在各个厂商的私有系统里，如果能像文件一样标准化、可移植，Agent 生态才能真正繁荣。
- **为什么重要**：Agent（智能体）是 2026 年 AI 领域最热的关键词之一，但记忆机制一直是碎片化、私有化的。如果“记忆文件格式”成为标准，Agent 就能在不同的系统间迁移、共享经验——这相当于给 AI 安上了“可携带的长期记忆”。
- **跟我有啥关系**：如果你在游戏里做了 AI 驱动的角色（比如会记住玩家行为的 NPC），这种“记忆文件化”思路可以直接借鉴——把 NPC 的状态记录成结构化文件，方便存档、继承和调试。
- **分析**：亮点是视角独特，把软件工程里的“文件格式标准化”思路引入 AI 领域；风险是标准之争历来残酷，可能最终各厂商还是各玩各的；值得跟进的是有没有重量级玩家（如 OpenAI、Anthropic）表态支持类似方案。

### 遇到的问题和卡点

- **FunASR/SenseVoice 单字 Token 导致多字连词匹配失效**：“所以”、“如果”等双字连词被拆成单字后，无法被原有规则正确识别，导致“老命啊所以”这类粘连问题反复出现。
- **纯分词规则在句法依存上的局限性**：jieba 分词虽然解决了词语腰斩问题，但系动词“是”、结构助词“的”、主语代词“我”等仍然会出现非自然截断，说明分词规则无法完全替代句法理解。
- **剪映音效素材类型不兼容**：音效素材使用简化的 `type=audio` 导致剪映无法识别为可编辑独立轨道，需要改为剪映真实工程中的 `type=sound` 和 `type=music`。
- **字幕识别源判断困难**：本机剪映虽有 `speechsdk.dll` 和 ASR 模型，但未发现稳定命令行识别入口，无法直接复用剪映的语音识别能力。
- **Windows 强制重启问题未根治**：`lsass.exe` 崩溃（RPCRT4.dll 模块、0xc0000005 异常）原因仍未完全确定，最高怀疑方向是 Windows 11 Build 26200.9168 / 8 月更新与代码完整性、内存完整性、第三方输入法/安全软件残留/音效驱动之间的兼容冲突。

### 怎么突破的

- **连词匹配失效 → 前向滑动窗口字符级检测**：不再依赖分词结果，改为在字符流上做前向 6 字符动态探测（`lookahead_text`），从源头绕开 ASR 单字 Token 的限制，实现了连词 100% 前置独立成句。
- **分词局限性 → 深度诊断 + 双路线归档**：先承认“纯规则有天花板”这一事实，然后把两条工业级破局路线（LLM 语义重构、依存句法树）完整写入交接文档，让下一任接手者可以直接沿着路线推进，而不是重新踩坑。
- **剪映音效不识别 → 逆向真实工程格式**：直接打开剪映生成的真实工程文件做对比，发现音频素材应使用 `type=sound`、BGM 使用 `type=music`，补齐资源字段后问题解决。
- **ASR 入口缺失 → 明确策略转向**：放弃“硬找命令行入口”的思路，改为“外部字幕源优先 + SenseVoice + 上下文纠错层”的策略，先保证流程可跑通，后续再迭代优化。
