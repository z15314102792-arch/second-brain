## 1. AI动态

### ★★★ [Tencent Releases and Open-Sources Tencent Hy4 Preview](https://www.tencent.com/tencent-releases-and-open-sources-tencent-hy4-preview/)
- **发生了什么**：腾讯发布了 Hy4 大模型的预览版并宣布开源。Hy4 是腾讯自研大模型的第四代产品，从命名和节奏来看，应该是接替此前混元（Hunyuan）系列的新一代模型。开源意味着开发者可以下载模型权重，在本地或自建服务器上部署推理，而不仅仅是通过 API 调用。
- **为什么重要**：国内大模型厂商的开源动作一直备受关注，腾讯此次开源 Hy4 预览版，一方面展示了自研模型的实力，另一方面也是在开源生态中争夺开发者心智。对于依赖 GitHub Pages 部署静态站点的个人开发者来说，这代表着未来在低成本下使用国产大模型的可能性在增加。
- **跟我有啥关系**：如果你正在做的小游戏需要接入 AI 能力（比如 NPC 对话、关卡生成、玩家行为分析），Hy4 开源后你可以在本地跑模型，省去 API 调用费用。而且开源模型没有 API 限流问题，适合做原型验证。
- **分析**：腾讯开源大模型的动作值得跟进，但目前只是"预览版"，实际效果和生态成熟度还需要观察。建议先关注社区评测和量化版本的可用性，不要急着迁移现有方案。

### ★★★ [OpenAI 宣布终止 Cursor 合作：SpaceX 收购后的连锁反应](https://openai.com/index/our-decision-on-cursor-following-its-acquisition-by-spacex/)
- **发生了什么**：OpenAI 官方发布声明，宣布在 Cursor 被 SpaceX 收购后，决定终止与 Cursor 的合作关系。Cursor 是目前最流行的 AI 代码编辑器之一，此前深度集成了 OpenAI 的模型。SpaceX 收购 Cursor 后，OpenAI 选择切割关系，意味着 Cursor 未来将不能再使用 OpenAI 的模型服务，需要转向其他模型供应商。
- **为什么重要**：这是 AI 编程工具领域的一次重大洗牌信号。Cursor 的崛起很大程度上依赖 OpenAI 的模型能力，如今两者分道扬镳，一方面会促使 Cursor 加速接入其他模型（如 Anthropic、Google），另一方面也说明 AI 应用层公司对底层模型供应商的依赖风险正在显现。
- **跟我有啥关系**：如果你在用 Cursor 写小游戏代码，未来 Cursor 的模型底座可能会换，界面和交互可能不变但代码生成质量会有变化。建议留意 Cursor 后续的模型切换公告，如果生成质量下降，可以考虑切换到其他 AI 编程工具。
- **分析**：这件事的深层影响是：AI 应用层公司开始意识到不能把所有鸡蛋放在一个篮子里。Cursor 被 SpaceX 收购本身就充满戏剧性，OpenAI 的切割更像是对"竞争对手阵营"的明确表态。对开发者来说，多掌握几个 AI 工具总是没错的。

### ★★★ [Warp 基于 Claude 构建自我改进型 AI Agent](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)
- **发生了什么**：Warp（知名终端应用）在 Anthropic 官方博客上分享了他们如何基于 Claude 构建自我改进型 Agent 的经验。Warp 将 Claude 集成到终端工作流中，让 AI Agent 能够根据用户的操作反馈持续优化自身的行为策略，实现"自我改进"。
- **为什么重要**：这是 Anthropic 官方博客发布的案例研究，说明 Claude 在企业级 Agent 场景下的实际落地效果。自我改进型 Agent 是目前 AI 应用的前沿方向，Warp 的实践为其他开发者提供了一个可参考的架构范式。
- **跟我有啥关系**：你在终端里使用 AI 辅助开发时，可以借鉴 Warp 的思路——让 AI 记录你的操作习惯和偏好，逐步优化它的建议方式。不过对于小游戏开发来说，这可能有点重，更实际的做法是给 AI 设定明确的代码风格和项目约束。
- **分析**：Warp 的案例值得关注，但"自我改进"目前更多是工程层面的渐进优化，距离真正的自主进化还有距离。作为个人开发者，不必追求这种复杂度，把基础的工作流跑通更重要。

### ★ [vLLM v0.28.0 发布](https://github.com/vllm-project/vllm/releases/tag/v0.28.0)
- **发生了什么**：vLLM 发布了 v0.28.0 版本。vLLM 是目前最流行的大模型推理加速框架，广泛用于本地和云端的大模型部署。新版本通常会包含性能优化、新模型架构支持和稳定性修复。
- **为什么重要**：vLLM 的每次更新都直接影响大模型推理的效率和成本。如果你关注本地部署开源模型，vLLM 的迭代速度和质量是重要的风向标。
- **跟我有啥关系**：如果你打算在本地跑开源模型（比如上面腾讯开源的 Hy4），vLLM 可能是你部署时的核心依赖。关注新版本的性能提升，可能意味着同样的硬件能跑更大的模型。
- **分析**：vLLM 的版本更新属于常规迭代，不必过度关注。但值得留意的是，如果 Hy4 开源后社区有 vLLM 适配，那部署门槛会大幅降低。

### ★ [Debian 投票允许"负责任地使用生成式 AI"](https://lwn.net/Articles/1091231/)
- **发生了什么**：Debian 项目通过投票，决定允许在项目开发中"负责任地使用生成式 AI"。此前 Debian 社区对 AI 生成代码持保守态度，这次投票结果标志着开源社区对 AI 辅助开发的态度正在松动。
- **为什么重要**：Debian 是最大的社区驱动的 Linux 发行版之一，它的态度会影响整个开源生态对 AI 生成代码的接受度。这可能是开源社区从"抵制 AI 代码"转向"规范 AI 代码"的分水岭。
- **跟我有啥关系**：你在 GitHub Pages 上托管小游戏项目，如果以后想用 AI 生成的代码提交到开源项目，Debian 的这个决定是个积极信号——只要负责任（比如标注 AI 生成部分、人工审查），社区接受度会越来越高。
- **分析**：这个投票结果更多是象征意义，实际执行细则还没落地。但方向是明确的：AI 辅助开发正在成为常态，与其抵制不如规范。

- **Antigravity 启动失败**：VS Code 扩展和终端 `agy` 两种方式均无法稳定启动，扩展日志显示 backend 启动超时，且曾把整个 `C:\` 作为工作区传入（`--add-dir=c:\`），问题涉及网络、代理、路径、缓存等多个因素叠加。

### 怎么突破的

- **代理问题**：通过带代理环境变量启动 `agy.exe` 解决，验证了直连超时、走 `127.0.0.1:7897` 可连通的根因，最终封装为 `gemini-pro` 命令自动设置代理。
- **整体方向**：在 Antigravity 启动失败无法快速解决的情况下，果断收口暂停，避免继续消耗时间和 Codex Plus 额度。转而聚焦"用户能用什么"——用 `gemini-pro` 命令作为稳定入口，满足用户使用 Gemini Pro 套餐的需求。

### 可以改进的地方

- **遇到多因素叠加的问题时，先判断"值不值得修"再动手**：Antigravity 启动失败涉及网络、代理、路径、缓存多个层面，排查成本已经超过收益。以后可以设一个时间盒（比如 30 分钟），超时后先收口记录，换一条路再试。
- **代理环境变量是个高频坑**：在 Windows 上使用任何需要联网的 CLI 工具，如果发现连接超时，第一反应应该是检查代理环境变量是否被继承，而不是怀疑账号或网络问题。
- **创建新命令时，先验证"最小可用路径"再封装**：`gemini-pro` 命令的成功是因为先手动验证了"带代理启动 agy.exe 可进入"，然后再封装成命令。以后做类似包装，应该先手动跑通，再写脚本，避免把不稳定因素也封装进去。
