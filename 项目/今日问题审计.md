## 二、根因分析（8 个根因，按深度分层）

### 第一层：操作失误（症状）

- `git add -A` 无差别暂存
- CLAUDE.md 编号错位
- 推送前不检查暂存区

### 第二层：流程缺陷

**根因 1：点对点灭火，不系统性扫描**
修 bug 时只修报错指向的那个点，从不主动扩大扫描半径。
例如：gitignore 只加 `remotely-save`，不想"还有什么其他插件目录"。

**根因 2：CLAUDE.md 规则缺乏执行触发器**
规则是静态文本，执行依赖 AI 主动回忆。没有强制触发机制。
例如："发现 bug 扫全盘"写了但没触发。

**根因 3：git 工作流对第三方写入无防御**
`git add -A` 是"信任型命令"，但 Obsidian 插件会随意写入仓库。
信任型命令放在不信任型环境里必然出问题。

**根因 5：方案推荐的"环境适配验证"缺失**
推荐方案时只关注"技术上能不能做"，不关注"用户环境下能不能用"。
例如：OneDrive 同步在移动网络被墙。

### 第三层：思维模式缺陷（最深）

**根因 4：效率质量冲突时 AI 单方面选择效率**
用替代方案偷偷替换用户的选择，不摊开来讨论。
例如：用户选"另写摘要"，我觉得贵就给了"去标记"。

**根因 6：隧道视野——在方案内死磕，不跳出审视**
把当前方案当成唯一方案，在内部优化而不跳出来问"这个方案本身是不是选错了"。
例如：Hook 关键词修 3 轮，没想"关键词匹配本身就是脆弱的方案"。

**根因 7：因果颠倒——用方法套需求，而非需求推方法**
默认思维路径："我有哪些工具→用哪个"，而非"用户要什么→什么方式最简单→需要什么工具"。
例如：备份="git bare repo"，跳过了"用户要什么"的分析。

**根因 8：不搜索不学习——遇事脑补而非查证**
默认自己想办法，不先看别人怎么做。
例如：Hook 关键词自己写，不去搜社区现成方案。

## 四、关键认知

1. **CLAUDE.md 规则本质是"建议"不是"约束"**——这是 Claude Code 的架构设计，不是 bug。规则作为用户消息注入，模型会在长对话中自行降权。
2. **Hooks 是唯一可靠的强制执法机制**——"Always/Never"类规则应该用 Hook 而不是 CLAUDE.md 文本。
3. **Skills 每轮被检索**——比 CLAUDE.md 只加载一次更可靠。高频规则应该迁移到 Skill。
4. **用结构替代意识**——AI 没有元认知，但可以用结构化的强制检查流程替代。社区的 Assumption Trace、Think-Before-Coding、Reflect Skill 都是这个原理。
5. **跨会话学习不是"写备忘录"**——记忆文件是静态文字，不会在工具调用前自动触发。需要在每次工具调用前后注入相关提醒（PreToolUse Hook）。
