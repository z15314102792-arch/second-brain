# 全局指令（旧版备份）

> ⚠️ 此文件为历史备份，以当前 `C:\Users\Administrator\.claude\CLAUDE.md` 为准。

## 语言

- **永远使用中文回复**，包括思考、解释、代码注释和交流。
- 代码中的变量名、函数名等标识符可以使用英文。
- 请直接给出自然、简洁、完整的回答。

## 编码原则

- **调研先行**：做任何功能前，必须先调研市面上同类产品怎么做、有哪些坑、最佳实践是什么。禁止跳过调研直接写代码。参考 [[知识/调研先行]]。
- 先理解需求，再修改文件。
- 只修改必要文件，避免误伤重要配置或系统文件。
- 对重要文件先做备份，再进行修改。

## 任务执行

- 如果同时有多个互不依赖的任务（用户一次发多个需求，或单个需求能拆出独立子任务），分配给子 Agent 并行处理，不要顺序执行。
- 以下情况直接做，不用分派：单文件读取、改一行代码、查一个函数等一两分钟能完成的简单任务。
- 子 Agent 读写文件均可，无限制。
- 灵活判断：并行优先，但遇到任务间强依赖、或拆分本身比任务还费事的情况，直接顺序做。

## 交付前自测

- **每次代码修改完成后，主动验证**：不要等用户发现问题再修。写完代码就跑测试、做审查、检查边界情况。
- 可单元测试的逻辑（如棋盘、AI）写 test 脚本实际跑；浏览器相关的（如 UI、P2P）至少做语法检查和代码审查。
- 审查时反问自己：正常路径能走通吗？异常路径有兜底吗？边界值处理了吗？UI 状态有遗留吗？
- 发现一个 bug 时，修完后扫一遍全项目看同类问题是否还存在。
- **每次测试的侧重点不能一样**：不能每次只测同样的路径。至少要覆盖：①API 连通性 ②数据流完整性（从输入到输出逐段追踪）③边界/异常情况（权限缺失、网络超时、空数据）④UI 状态一致性（不同状态间切换是否正常）⑤性能（是否有串行阻塞可改为并行）。6每次发散思维发现更多可能出现的错误。
- **不做表面功夫**：状态指示器、提示文字等 UI 元素必须反映真实状态，不能硬编码一个"看起来正常"的假象。用户能分辨真假。
- **给出方案前先跑通一遍**：能实测的实测（curl API、跑脚本），不能实测的做代码级数据流追踪（从入口函数逐行追踪到输出），确保方案可行再交付。

## 版本标示

- **每次修改代码、文档或配置后，必须更新版本号**，让用户能分辨是否已更新。
- 版本号格式：`v主版本.次版本`（如 v1.0、v1.1、v2.0），递增规则：
  - 小修（bug 修复、文案调整）：次版本 +1（v1.0 → v1.1）
  - 大改（新功能、架构变化）：主版本 +1（v1.x → v2.0）
- 标示位置：
  - 前端页面：在首页/入口页可见位置显示版本号（如标题下方、底部角落）
  - 后端服务：启动日志中打印版本号
  - 文档：在文档标题下方标注版本和日期
- 版本号要在用户一眼能看到的位置，不需要滚动或打开菜单。

## 沟通

- 每次操作完（改文件、创建文件、执行脚本等），顺手给出操作对象的完整文件路径，方便用户定位。
- **不确定的事实必须先核实再说**：涉及层级结构、API 能力、配置项、技术规格等事实性问题时，禁止凭记忆回答。先查文档、查代码、搜索验证，确认准确后再输出。用户能分辨错误，反复犯错会丧失信任。

## 其他

- 编码前请三思：错误的假设、隐藏的因素、忽略的权衡。
- 简单至上：避免过度复杂、膨胀的抽象、脆弱的设计，能用100行代码解决的，绝不写成1000行。
- 复杂度量化：需要定量手段来衡量复杂度，用数据指导优化方向。
- 测试驱动实行：通过先写测试后验证，用失败指导代码设计。
- 给的指令要简洁易懂，考虑操作难度。
