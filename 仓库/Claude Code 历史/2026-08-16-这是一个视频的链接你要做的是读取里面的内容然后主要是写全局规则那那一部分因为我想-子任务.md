# 一、写规则的心智模型（先看这张总表）

官方把持久化配置分成了 5 个层次，判据是两问：**「这条信息每次会话都要用吗？」** 和 **「它必须 100% 发生，还是 Claude 判断一下就行？」**

| 想表达的内容 | 放哪里 | 加载时机 | 官方依据 |
|---|---|---|---|
| 项目级事实/约定/常用命令，每次会话都要用 | 项目根 `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 每次会话启动注入 | [memory 文档](https://code.claude.com/docs/en/memory) |
| 个人偏好，跨项目通用 | `~/.claude/CLAUDE.md` | 每次会话 | 同上 |
| 按主题拆分的规则（代码风格、测试、架构） | `.claude/rules/*.md` | 无 `paths` 则常驻；有 `paths` 则**匹配到文件路径才加载** | 同上（#organize-rules-with-claude/rules） |
| 必须确定性发生的事（格式化、跑测试、拦截危险命令、阻止提交到受保护分支） | **hooks**（settings.json） | 事件触发，**无条件执行，不经过模型判断** | [hooks 文档](https://code.claude.com/docs/en/hooks) |
| 流程性/检查清单/长篇参考，用的时候才要 | **skills**（`.claude/skills/<name>/SKILL.md`） | 按需调用，平时不占上下文 | [skills 文档](https://code.claude.com/docs/en/skills) |
| 会话中 Claude 学到的东西（纠错、偏好、项目决策、外部系统指针） | **auto-memory**（`~/.claude/projects/<路径>/memory/`） | 索引 MEMORY.md 每次会话加载（前 200 行），细节按需 | [memory 文档](https://code.claude.com/docs/en/memory) |
| 需要独立上下文/专业化工具限制/并行/省钱的任务 | **subagents**（`.claude/agents/*.md`） | 主对话委派时 | [sub-agents 文档](https://code.claude.com/docs/en/sub-agents) |

一句话总结：**CLAUDE.md / rules = 上下文与建议（Claude 会读、可能选择性忽略）；hooks = 强制（100% 执行）；skills = 按需加载的知识包；memory = 会话间自动积累的笔记；subagents = 分工。** 官方反复强调：CLAUDE.md 是"context，不是 enforcement"，必须发生的事用 hook（来源：[memory 文档](https://code.claude.com/docs/en/memory)、[hooks 文档](https://code.claude.com/docs/en/hooks)）。

# 二、CLAUDE.md：该写什么 / 不该写什么

官方定位：CLAUDE.md 放「每个会话都应生效的项目指令：编码标准、常用命令、架构上下文、团队约定」。所有文件（含子目录里的 CLAUDE.md）按层级**拼接**（不是覆盖），越靠近启动目录的读得越晚。（来源：[memory 文档](https://code.claude.com/docs/en/memory)）

**官方建议写**（社区对官方要点的归纳，来源：[morphllm 指南](https://www.morphllm.com/claude-md-guide)）：
- 项目一句话概述（是什么/为什么/怎么跑）
- **Claude 猜不出来的命令**（构建、测试、lint、dev server、指定测试文件的具体命令）
- 项目结构要点（关键目录用途）
- 偏离默认的代码风格与命名约定
- 测试要求、架构边界（如"handler 不许直接碰 DB"）
- Git 约定、安全规则
- **"不许做什么"清单**（禁令比建议更有约束力，如"NEVER use `any`"、"不要硬编码密钥"）

**官方/社区一致反对写**：
- **能从代码里读出来的东西**——通用语言惯例、逐文件描述、文件路径（这些信息代码和 git 里都有，写进去纯浪费上下文）
- 详细 API 文档/长解释——应改成链接（`@docs/api-patterns.md`）
- 频繁变化的信息——引用而不是内嵌
- 长教程/散文
- 属于 linter/formatter 的格式规则——交给工具，不写进 CLAUDE.md
- 只有特定目录才用的知识——移到 `.claude/rules/` 加 `paths`，或做成 skill（按需加载，省上下文）

**何时该往 CLAUDE.md 加一条**（官方 heuristics，来源：[memory 文档](https://code.claude.com/docs/en/memory)）：
1. Claude 同一个错误犯了**第二次**
2. code review 逮到 Claude 本该知道的关于本代码库的事
3. 你输入了和上次会话**一模一样的更正**
4. 一个新同事要干活也**需要同样的上下文**

Anthropic 内部实践是"每个错误都变成一条规则"——PR review 里 Claude 犯错，就把规则补进 CLAUDE.md，让它不再犯（来源：[morphllm 指南](https://www.morphllm.com/claude-md-guide)）。

# 三、Memory（自动记忆）机制

官方把记忆分成两个互补系统：**CLAUDE.md（你手写、进 git）** 和 **auto-memory（Claude 自己写、不进 git）**。auto-memory 默认开启。（来源：[memory 文档](https://code.claude.com/docs/en/memory)）

- **存哪**：`~/.claude/projects/<路径>/memory/`，按 git 仓库隔离，本机私有。
- **MEMORY.md 是索引**：每条一行、<150 字符，格式 `[标题](文件.md) — 一句话说明`，不写正文。**会话启动只加载前 200 行或 25KB**，其余细节放主题文件（`user_role.md`、`feedback_testing.md` 等），按需读取。
- **四种类型**（每个记忆文件 YAML frontmatter 带 `name`、`description`、`type`）：

| 类型 | 存什么 | 典型触发 |
|---|---|---|
| `user` | 角色、专长、偏好、目标 | "我是数据科学家" |
| `feedback` | 纠错**和确认**（附 Why / 怎么用），不只存失败，也要存用户验证过的好做法 | "别 mock 数据库"、"单个 PR 更好" |
| `project` | 截止日、事故、决策、代码里看不出的上下文 | "周四开始冻结合并" |
| `reference` | 外部系统的指针（Linear/Slack/面板） | "管道 bug 在 Linear INGEST 项目里" |

- **明确不存**（官方：即使你要求保存也不存）：能从代码库推导的代码模式/架构/文件路径/项目结构、git 历史、代码里已有的调试方案、CLAUDE.md 已有的内容、临时的会话任务细节。核心原则：**"只存无法从当前项目状态推导出来的信息。"**
- **管理**：`/memory` 命令查看/编辑；直接说"记住……/忘掉……"也行。

# 四、Rules 机制（.claude/rules + 条件加载）

规则文件是**按主题拆分 CLAUDE.md 的模块化方案**，`.claude/rules/` 下所有 `.md` 递归发现，可建子目录（如 `frontend/`、`backend/`）。（来源：[memory 文档 #organize-rules-with-claude/rules](https://code.claude.com/docs/en/memory)）

- **无 `paths` 前言的规则**：与 CLAUDE.md 同优先级、**每次会话常驻加载**（同样建议单文件 <200 行）。
- **带 `paths` 前言的规则**：**只在 Claude 处理匹配路径的文件时才注入**——这是控制常驻上下文大小的主要手段。官方格式：

```yaml
---
paths:
  - "src/api/**/*.ts"
  - "src/routes/**/*.ts"
---

# API 开发规则
```

- 用户级规则在 `~/.claude/rules/`，**先于**项目规则加载，项目规则优先覆盖个人偏好；可用软链接跨项目共享规则。
- ⚠️ 注意：`paths` 前言的语法在多个版本里被报过坑（[#16038](https://github.com/anthropics/claude-code/issues/16038)、[#17204](https://github.com/anthropics/claude-code/issues/17204)、[#22170](https://github.com/anthropics/claude-code/issues/22170)），有用户反映 YAML 数组/带引号写法静默失效、也有说要用 `globs:` 字段。社区结论：优先试 YAML 数组格式 `paths:` 列表；失效再试单行不带引号的 CSV 或 `globs:`。**文档写法不稳定，落地时要实际验证。**

# 五、Hooks：什么该用 hook 而非规则

官方判据：**"如果它是建议，用 CLAUDE.md；如果它是硬性要求，用 hook。"**（来源：[morphllm 指南](https://www.morphllm.com/claude-code-hooks) 归纳官方观点）hooks 是**确定性、非 AI 的 shell 命令/HTTP/提示词/agent**，在生命周期事件自动触发，把"最佳实践"变成"强制执行"——格式化永远会发生，而不是等 Claude 想起来。（来源：[hooks 文档](https://code.claude.com/docs/en/hooks)）

**该用 hook 的行为**：
- 必须在特定时机 100% 发生的事：每次编辑后自动格式化（Prettier/Black/gofmt）、每次改动后跑测试
- 拦截/阻止类：PreToolUse 阻止 `rm -rf`、阻止读 `.env`、阻止 `git push --force`、阻止提交到受保护分支
- 验证类：Stop 钩子检查 transcript 里有没有跑过测试，没有就拒绝结束并提示"先跑测试"

**不该用 hook**：建议性、需要判断力的行为留在 CLAUDE.md。关键事件：`PreToolUse`（唯一能阻止工具调用的事件，exit 2 阻断并回喂 stderr）、`PostToolUse`（格式化/lint/日志）、`Stop`、`Notification`。配置在 settings.json（`~/.claude/settings.json` 用户级、`.claude/settings.json` 项目级、`.claude/settings.local.json` 私有级）。

# 六、Subagents / Skills：官方怎么说

**Subagents**（`.claude/agents/*.md`）：带 YAML frontmatter 的 Markdown，**独立上下文窗口**、可限工具、可换更便宜的模型。官方建议用的场景（来源：[sub-agents 文档](https://code.claude.com/docs/en/sub-agents)）：
- 副作用任务会**淹没主对话**（大量搜索结果/日志/文件内容以后不再引用）——让 subagent 在自己的上下文里干完只回摘要
- 你**反复生成同一个工种的 worker**（同一套指令）——定义一次复用
- 需要**限定工具**（review 类 agent 不给 Write/Edit）
- 需要**省钱**（简单任务路由给 Haiku）
- 官方博客补充：**"先研究后实现"** 模式（委派代码库调研）和并行修改（[claude.com/blog/subagents-in-claude-code](https://claude.com/blog/subagents-in-claude-code)）

**Skills**（`.claude/skills/<name>/SKILL.md`）：按需加载的可复用工作流/知识包，平时不占上下文。官方触发场景（来源：[skills 文档](https://code.claude.com/docs/en/skills)）：
- 你**反复往聊天里粘贴同一份步骤/清单/多步流程** → 做成 skill
- CLAUDE.md 里某部分**从"事实"演化成了"流程"** → 移进 skill
- 判据："如果你发现自己在 CLAUDE.md 里写『每次都要按这些步骤』，就改成 skill"
- 不适合 skill：一行小指令、变化很大的流程、项目专属命令（后者留 CLAUDE.md）

# 七、长度与排版

- **长度硬指标**：官方建议**每个 CLAUDE.md 文件 <200 行**，Claude Code 团队自己的文件约 **100 行 / 2,500 tokens**。超过会降低遵守度——Claude 会开始选择性忽略，尤其文件末尾。（来源：[morphllm 指南](https://www.morphllm.com/claude-md-guide) 归纳官方观点）规则文件同理 <200 行。
- **语气**：官方文档**没有**规定第一/第二人称（第二人称是第三方建议）。官方强调的是**祈使句 + 具体可验证**："Use 2-space indentation" 而不是 "Format code properly"；"Run `npm test` before committing" 而不是 "Test your changes"。禁令与替代要成对："Never use `--foo`; use `--bar` instead"。（来源：[memory 文档](https://code.claude.com/docs/en/memory) + 社区共识）
- **强调词**：`IMPORTANT:` / `YOU MUST:` / `NEVER:` 可用但**克制**——如果每条都是 IMPORTANT，就都不是。
- **结构**：用 Markdown 标题和列表分节；定期清理过时/冲突规则；monorepo 用 settings.json 的 `claudeMdExcludes` 跳过无关 CLAUDE.md。
- **省 token 技巧**：**HTML 注释 `<!-- ... -->` 会被剥离**，可放只给人看的维护说明（零成本）；`@path/to/file` 导入只是组织内容，**不省上下文**（启动时就展开）。
- **本地私有**：`./CLAUDE.local.md` 自动进 .gitignore，放个人环境 URL/私人备忘。
- **压缩行为**：`/compact` 后根 CLAUDE.md 会重新注入，但对话里的重要指令会丢——重要约定要提升进 CLAUDE.md 而不是留在对话里。（来源：[memory 文档](https://code.claude.com/docs/en/memory)）

# 八、给你的落地建议（针对你在优化的中文全局 CLAUDE.md）

对照你的 `~/.claude/CLAUDE.md`（当前约 60 行，含语言/调研/思维模式/任务执行/自测/版本/沟通/存档/编码原则/防振荡），按官方心智模型分层：

1. **留在 CLAUDE.md**（常驻、每次都要）：语言用中文、沟通习惯（小白友好、给完整路径）、会话存档规则、版本标示、防振荡规则。这些是"每次会话都要生效的约定"，符合官方定位。
2. **移去 `.claude/rules/`（用户级 `~/.claude/rules/`）**：按主题拆——`research.md`（调研先行、卡点调研、环境校验三问）、`communication.md`（沟通规范）、`self-test.md`（自测五维度）。你现在的全局文件已接近 200 行上限，拆分后常驻量反而小。
3. **考虑做成 skill 的**：`保存进度`（已经有这个 skill 了）、"Think-Before-Coding 协议"如果它是一套多步流程，符合官方"流程→skill"判据。
4. **该用 hook 的（如果涉及强制）**：全局 CLAUDE.md 里的"会话存档/验收脚本"如果要求**必须执行**，官方逻辑是——建议性用文档，强制用 hook。目前你的是软约束（skill 实现），可以保持。
5. **auto-memory 不重复存**：你 CLAUDE.md 里已有"第二大脑备份"、用户画像等，官方明确"CLAUDE.md 已有的内容不进 memory"，避免两处重复。
