# 公开社区深度调研

> 目的：把“先调研再行动”变成可直接执行的标准流程。与 [[知识/调研先行]] 配套：前者回答“为什么先调研”，本文件回答“具体怎么调研”。

## 触发方式

当用户说以下任意类似表达时，默认调用本流程，不必再询问是否要跨平台：

- “按调研协议调研 X”
- “按社区地图调研 X”
- “深度调研 X”
- “找找有没有类似项目 / 可二开的项目”
- “看看这个东西值不值得做”
- “帮我找现成方案，不要重复造轮子”

未指定深度时，默认使用 **标准调研**。

## 总原则

1. **不只搜 GitHub。** GitHub 主要回答“别人做了什么、代码怎么实现”；真实痛点、产品趋势、模型、数据、论文要去对应社区找。
2. **先需求，后方案，再实现。** 先确认有人真的需要，再查现有产品，最后才看代码和技术。
3. **先复用，后改造，最后才从零开发。** 默认顺序：直接使用现成工具 → 调 API/组合工具 → Fork 二开 → 从零开发。
4. **多源交叉验证。** 官方宣传、项目 README、单个网友观点都不能单独作为结论。
5. **时间敏感。** AI 与开源生态变化快，优先近期仍活跃的信息；热门但长期停更的项目自动降级。
6. **结论优先。** 最终要回答“值不值得做、最优路线是什么、下一步做什么”，而不是堆链接。

# 一、社区地图：去哪找什么

| 来源 | 主要用途 | 重点看什么 | 什么时候优先 |
|---|---|---|---|
| GitHub | 开源项目、代码、库、工具、二开机会 | Star/Fork 仅辅助；Commit、Release、Issue、PR、License、维护状态更重要 | 找实现、找可复用项目、判断二开 |
| GitLab | GitHub 补充，DevOps/企业项目 | 活跃度、CI/CD、License | GitHub 结果不足或企业/DevOps 场景 |
| Reddit | 真实用户痛点、吐槽、替代方案、使用体验 | 高频重复问题、抱怨、付费意愿、替代工具 | 找需求、验证用户是否真的痛 |
| V2EX | 中文开发者/国内用户反馈 | 国内环境、价格、部署、网络、中文需求 | 需要中文用户视角时 |
| Product Hunt | 新产品、AI 工具、SaaS、竞品 | 产品定位、卖点、发布时间、竞品密度 | 找“别人已经做了什么” |
| Hacker News | 技术趋势、创业产品、开发者讨论 | Show HN、讨论质量、技术趋势 | 判断方向是否升温、看开发者反馈 |
| Hugging Face | 模型、数据集、Spaces/Demo | License、模型大小、硬件需求、下载量、维护状态 | 涉及 LLM/OCR/ASR/TTS/图像/视频/Embedding 等 AI 能力 |
| Kaggle | 数据集、Notebook、分析案例 | 数据质量、许可、Notebook 实现 | 任务依赖数据、需要机器学习案例 |
| Stack Overflow | 技术问答、历史排错 | 高票答案、版本时间、官方引用 | 验证具体技术问题 |
| 官方文档 | API、规格、限制、最新行为 | 版本、发布日期、限制、授权 | 所有关键技术结论的优先证据 |
| arXiv / 论文 | 前沿算法、模型、技术源头 | 方法、实验条件、是否已有实现 | 前沿技术或可行性不确定时 |
| Discord / 官方社区 | 项目真实活跃度、Roadmap、用户反馈 | 开发者响应、常见问题、插件生态 | 候选项目进入最终 Top 3 后深挖 |
| 官方产品站 / 定价页 | 商业产品能力与价格 | 价格、套餐、限制、隐私、部署方式 | Buy vs Build 判断 |

## 不机械全搜

根据问题自动选源：

- **找产品机会**：Reddit/V2EX → Product Hunt/HN → GitHub → 必要时 HF/Kaggle
- **找开源二开项目**：GitHub/GitLab → Issues/Discussions → Reddit/HN → 官方文档
- **找 AI 能力**：Hugging Face → GitHub → 官方论文/文档 → Reddit/HN 使用反馈
- **解决技术卡点**：官方文档 → GitHub Issues → Stack Overflow → Reddit/项目社区
- **判断一个想法值不值得做**：需求社区 → 竞品 → 开源实现 → 技术/成本 → 反证

# 二、标准调研流程

## 第 0 步：定义问题

先把问题转换成可验证的研究问题：

- 用户是谁？
- 现在怎么解决？
- 具体浪费什么：时间、钱、精力、准确率、稳定性？
- 最终想要的是工具、产品、自动化、学习项目还是商业机会？
- 有哪些硬约束：本地/云端、预算、隐私、设备性能、是否可编程、国内可用性？

如果用户表达模糊，AI 先根据上下文形成 1~3 个合理假设并标注；只有关键分歧会改变方向时才追问。

## 第 1 步：生成搜索关键词矩阵

不要只用用户原话。至少生成以下维度：

- 中文关键词
- 英文关键词
- 痛点表达：`pain / annoying / manual / tedious / alternative / wish there was / how do you` 等
- 产品表达：`tool / app / SaaS / open source / self-hosted / alternative`
- 技术表达：核心技术名、协议、模型、框架
- GitHub 表达：`awesome`, `self-hosted`, `workflow`, `automation`, `agent`, `plugin`, `template`
- 反向关键词：`abandoned`, `deprecated`, `issue`, `limitations`, `expensive`, `privacy`

搜索过程中发现新术语时，自动加入下一轮。

## 第 2 步：验证真实需求

优先搜索 Reddit、V2EX、论坛、Issues 等真实讨论。

记录：

- 痛点出现频率
- 是否多人独立提出相似问题
- 用户当前替代方案
- 替代方案最常被抱怨的缺点
- 是否有人愿意付费/已经付费
- 问题是偶发抱怨还是稳定需求

**需求证据强度：**

- A：多个独立社区/帖子长期重复出现，且有真实行为或付费
- B：多个用户重复提出，有明确替代方案
- C：少量讨论，有合理需求但证据不足
- D：只有作者/单个用户主观判断

## 第 3 步：查现有产品与趋势

搜索 Product Hunt、Hacker News、官方产品站、网页结果。

回答：

- 已有哪些头部/新兴产品？
- 核心卖点是什么？
- 收费模式和门槛？
- 用户为什么选择/放弃？
- 竞争是否已经过密？
- 最近一年是否出现明显新趋势？

不要把 Product Hunt 排名当真实市场占有率；它主要用于“发现产品”。

## 第 4 步：查开源实现

搜索 GitHub/GitLab。

对每个重点候选检查：

- 最近 Commit / Release 时间
- Contributors 数量及是否单人维护
- Issues：数量、最近回复、典型抱怨
- Pull Requests：是否正常合并
- README 是否只是 Demo 还是可部署产品
- 安装/部署复杂度
- 是否有 Docker / Windows / macOS / Linux 支持
- 是否有真实用户或插件生态
- License 是否允许个人/商业二开
- 是否存在安全、隐私、数据上传风险

**Star 只作为“被看见程度”的辅助信号，不作为质量分。**

## 第 5 步：按需寻找 AI 模型与数据

如果产品涉及 AI：

- Hugging Face：查模型、Spaces、数据集
- Kaggle：查数据集与 Notebook
- 官方模型文档：查 API、价格、上下文、调用限制
- arXiv：只有需要前沿算法或验证技术源头时再用

对模型额外检查：

- License
- 参数量/显存需求
- 推理速度
- 中文能力/目标语言能力
- 是否可本地运行
- 是否有量化版本
- 最后更新时间

## 第 6 步：跨平台交叉验证

至少对最终重点候选做两类不同证据交叉：

- 官方/仓库证据 + 用户社区反馈
- README 宣称 + Issues/Reddit 实际体验
- 产品功能 + 价格/限制页
- 模型榜单 + Demo/真实使用反馈

若来源冲突，明确写出冲突，不自行挑对用户更好听的一边。

## 第 7 步：反证与淘汰

对每个 Top 候选主动问：

- 为什么不应该选它？
- 是否停更？
- 是否只有高 Star 但几乎没人维护？
- 是否安装成本高于直接买现成产品？
- 是否 License 不适合？
- 是否需要高价 GPU/API？
- 是否中文/国内网络不可用？
- 是否只是 Demo，不适合长期使用？
- 用户真正痛点是否其实已被成熟产品解决？

符合明显致命条件时直接淘汰，不为了凑数量保留。

# 三、候选评分框架

评分用于横向比较，不制造虚假精确度。默认每项 1~10 分，并给一句理由。

| 维度 | 说明 |
|---|---|
| 需求匹配度 | 是否真正解决用户当前问题 |
| 实用性 | 能否稳定落地，不只是 Demo |
| 活跃度 | 最近 Commit/Release/Issue/PR |
| 成熟度 | 文档、测试、版本、用户基础 |
| 可二开性 | 架构、模块化、文档、License |
| 部署成本 | 环境、GPU、服务器、数据库、网络 |
| 学习成本 | 用户/AI 接手理解难度 |
| 维护成本 | 升级、依赖、社区、单点维护风险 |
| 社区质量 | Issues/Discord/Reddit 的真实活跃度 |
| 创新/差异化 | 相比现有方案是否有实际增益 |
| License/商业安全 | 是否允许目标用途 |
| 国内可用性 | 网络、支付、语言、平台限制（适用时） |

建议综合判断：

- **强推荐**：明显匹配，风险可控，可直接使用或二开
- **可用但有条件**：有明显限制，需要接受成本/改造
- **观察**：潜力大但不成熟
- **不推荐**：维护、成本、License、需求匹配等存在硬伤

# 四、Build / Buy / Fork 决策

调研结束必须明确推荐哪条路线：

1. **Buy / 直接使用成熟产品**：已满足 80%~100% 需求，自己做收益低
2. **API / 组合现有服务**：多个成熟能力拼装即可完成
3. **Fork / 二次开发**：已有项目完成约 60%~90%，改造成本显著低于重写
4. **从零开发**：现有方案有明确缺口，需求证据足、技术可行、长期维护值得
5. **暂时不做**：需求弱、竞争过密、成本过高、方案已成熟到没有必要重复做

优先级默认：**直接用 > 组合 > Fork > 从零开发**。

# 五、调研深度档位

## 快速调研

适合“先看看有没有”。

- 2~4 个核心来源
- 5~10 个候选
- 重点回答：有没有、最值得看哪几个、要不要继续深挖
- 不做全面论文/社区历史考古

## 标准调研（默认）

- 需求：Reddit/V2EX 等
- 产品：Product Hunt/HN/官方站
- 开源：GitHub/GitLab
- AI：Hugging Face（适用时）
- 数据：Kaggle（适用时）
- 官方文档与必要技术验证
- 最终 Top 3~5 候选做跨平台验证

## 深度调研

用于真正准备投入时间/金钱的项目。

在标准档基础上增加：

- Issues/PR/Release 历史
- Discord/项目社区
- License 深查
- 商业模式/价格/隐私
- 论文与技术源头
- 竞争格局
- 维护者与项目持续性
- 失败案例和反方意见
- 可二开架构与实施成本估算

# 六、停止条件

避免无限搜索。满足以下条件即可停止并给结论：

- 已找到至少 3 个有代表性的可行候选，或确认没有成熟候选
- 需求、产品、开源/技术三条证据链基本闭合
- 新增搜索结果开始重复，连续一轮没有改变排名或结论
- Top 候选的关键风险已验证
- 已足以判断 Buy / API / Fork / Build / 不做

如果证据不足，要明确写“目前证据不足”，而不是继续无限扩展搜索。

---

# 七、证据与时效规则

证据优先级：

1. 官方文档 / 官方仓库 / 原始论文 / 原始数据
2. 项目 Issues、PR、Release、开发者讨论
3. 多个独立真实用户反馈
4. 高质量媒体/第三方评测
5. 单一网友或二手转载

时间规则：

- AI 模型、API、产品价格、开源维护状态：优先近 6~12 个月
- 稳定技术原理可使用更早资料，但要确认版本仍适用
- 涉及“当前/最新/是否还维护”必须查近期来源

# 八、默认输出模板

## 1. 一句话结论

直接说：值得做 / 不值得做 / 更适合直接用 / 更适合 Fork，并说明核心原因。

## 2. 真实需求

- 谁在抱怨什么
- 频率与证据等级
- 当前替代方案

## 3. 市场与现有产品

- 头部/新兴产品
- 优势与缺口
- 竞争强度

## 4. 开源与技术候选

对重点候选给：

- 名称
- 解决什么
- 活跃度
- License
- 部署难度
- 优点
- 硬伤
- 是否适合二开

## 5. AI 模型/数据（适用时）

列出可复用模型、数据、API 与成本。

## 6. Top 候选排名

Top 1 / Top 2 / Top 3，并说明淘汰其他方案的原因。

## 7. Build / Buy / Fork 决策

明确推荐路线，不模棱两可。

## 8. 风险与反证

列技术、维护、License、成本、竞争、隐私、国内可用性等风险。

## 9. 下一步

只给最值得立即执行的 1~3 个动作。

# 九、执行纪律

- 不要只总结 README。
- 不要用 Star 代替质量判断。
- 不要把“有项目”误判成“项目成熟”。
- 不要把“有人抱怨”误判成“有商业需求”。
- 不要为了迎合用户想法，只找支持证据；必须主动找反例。
- 不要因为开源就默认可商用；必须看 License。
- 不要因搜索不到就立即判定不存在；换关键词、换社区、换语言再验证。
- 用户没有要求逐步确认时，允许 AI 自主扩展关键词、替换来源、淘汰候选、加深验证。

# 十、与第二大脑和开发流程衔接

调研开始前：

1. 先查第二大脑是否已有相关项目、知识、历史踩坑，避免重复调研。
2. 若已有旧结论，检查时效；过期内容不得直接当当前事实。

调研完成后：

- 长期有效的结论 → `知识/`
- 可重复执行的方法 → `技能/`
- 准备实际做的东西 → `项目/` 或 `待办/`
- 某工具的配置/规格 → `资料/`
- 当天调研过程与决策 → `日志/`

## 转入 Codex / 工程执行的条件

当以下四项基本明确时，停止继续泛调研，转入工程阶段：

- 产品/功能目标明确
- 已选定基础项目或技术路线
- License 与部署成本可接受
- Top 风险已有处理方案

进入工程阶段后，Codex 负责：读仓库、制定实现计划、改代码、跑测试、Debug、Review；本 Skill 继续用于遇到技术卡点时外部调研。

# 十一、最短调用指令

以后只需说：

> 按公开社区调研协议，对【X】进行标准调研。自主扩展关键词和信息源，不局限 GitHub；重点验证真实需求、竞品、开源实现、AI 模型/数据、二开机会和反证，最后给出是否值得做、最优路线与下一步。

如果用户只说“按调研协议调研 X”，视为同义调用。
